Big picture — what is Slice 2 doing?

Slice 1 built the schema. Nothing actually runs yet — you can't talk to the app and store a claim. Slice 2 changes that. By the end, the app has a real request/response cycle: HTTP request in, SQL write to Postgres, JSON response out.

Three new pieces are needed: Pydantic schemas to define what the API accepts and returns, a database session dependency to hand each route a DB connection, and route handlers that do the actual work.

How the pieces fit together

Before touching any file, it helps to know what job each one has. This slice touches four files — each is a separate ingredient, and the router is where they finally get combined:

app/db.py
Sets up the machinery for talking to Postgres: the engine, the session factory, and now, the per-request session provider (get_db). It never queries anything itself.
app/models/*.py
Describes what tables exist and their columns (already built in Slice 1).
app/schemas.py
Describes what shape the API's inputs and outputs are.
app/routers/claims.py
Is where all of the above finally get used together: receive a request, validate it with a schema, get a session via get_db, build a model instance, save it, return a schema.

Keep this shape in mind as you move through the remaining steps — db.py, models, and schemas are all just ingredients; the router is where the actual request/response logic lives.

Concept
Two sets of models — why does this exist?

After Slice 1, you have SQLAlchemy models in app/models/. Slice 2 introduces a second set: Pydantic schemas. This trips up almost everyone the first time.

💡 One sentence: SQLAlchemy models describe the database table. Pydantic schemas describe the API contract.

They serve different purposes and live at different layers:

SQLAlchemy model
→ maps Python class to Postgres columns. Used by the ORM to read/write rows.
Pydantic schema
→ defines JSON shape. Used by FastAPI to validate requests and serialise responses.

Why can't you use the SQLAlchemy model directly as the response shape? Several reasons:

The DB row often has fields you don't want to expose (internal flags, relationships). Request bodies often omit fields that the DB generates (UUIDs, timestamps). Response shapes may join or transform data. And SQLAlchemy objects carry session state that Pydantic can't serialise.

The naming convention you'll follow: ClaimCreate = what the caller sends, ClaimRead = what the API returns. The *Create schema has no id or created_at — those are server-generated. The *Read schema has them.

↕ Trade-off you're accepting: two parallel class hierarchies to maintain. For each new entity, you'll add both a model and a schema. Worth it — this boundary protects your API contract from DB internals.
Concept
Dependencies and Depends()

Every route that touches the database needs a session. You could open and close one inside each route function — but that's repetitive, error-prone, and hard to test. FastAPI's dependency injection solves this cleanly.

A dependency is a function FastAPI calls before your route handler and injects the result. You declare what you need as a parameter with a default value of Depends(some_function), and FastAPI calls that function for you, injects the result, and cleans up afterwards.

python
def get_db():
    db = SessionLocal()
    try:
        yield db        # ← hands the session to the route
    finally:
        db.close()      # ← runs after the route returns (even on exception)

@router.get("/claims")
def list_claims(db: Session = Depends(get_db)):
    return db.query(Claim).all()

You don't call get_db() yourself — FastAPI does. This is dependency injection: a way to share setup/teardown code across many routes without repeating it inside each one.

What yield means here

yield is a Python keyword that turns a function into a generator — a function that can pause, hand something back, and resume later.

Normal function: call → run to end → return value → done
Generator with yield: call → run until yield → pause, hand value to caller → caller does its work → resume after yield → run to end

In get_db(), the exact sequence of events is:

1. FastAPI calls get_db()
↓
2. Opens DB session: db = SessionLocal()
↓
3. Hits `yield db` — PAUSES, hands db to FastAPI
↓
4. FastAPI injects db into your route handler
↓
5. Your route runs (queries, commits, etc.)
↓
6. Your route returns
↓
7. FastAPI resumes get_db() after the yield
↓
8. finally block runs: db.close()
⚠ The try / finally wrapper is critical: finally runs regardless of what happened in step 5. If your route raises an exception, the session is still closed. Without it, a crashed route would leak an open DB connection.
💡 Hotel key card analogy: the receptionist (get_db) opens the room (DB session), hands you the key card (yield db), you use the room (route runs), hand the card back, and the receptionist locks up (db.close()). The receptionist manages open/close — you just use the room.
Where Depends() appears in later slices

This pattern repeats in every slice from here on. Here's exactly where you'll see it:

Slice 2 · now
DB session — db: Session = Depends(get_db). Every route that touches Postgres gets a session injected this way.
Slice 3
Testing — you'll override get_db in conftest.py to inject a test session that rolls back after each test. The routes don't change — you just swap the dependency. app.dependency_overrides[get_db] = get_test_db
Slice 4
Authentication — you'll write a get_current_user dependency that reads a JWT token from the request header and returns the authenticated user — or raises a 401. Every protected route does: current_user: User = Depends(get_current_user). Auth is enforced before the route body even runs.
Phase D
AI subsystem — when you wire the Claude API into routes (document extraction, claim triage), you'll inject a configured AI client the same way via get_ai_client. Same pattern, different resource.
✓ The mental model: Depends() is FastAPI's answer to "how do I share a resource (DB session, auth user, AI client) across many routes without repeating open/use/close logic in each one?" The dependency handles setup and teardown. The route handles business logic. They stay separate — which is why routes are easy to test and easy to read.
Concept
Full request lifecycle

Here's the complete sequence for a POST /claims request, so you can trace a bug at any step:

1. HTTP POST /claims arrives
↓
2. FastAPI reads request body JSON
↓
3. Pydantic validates against ClaimCreate — 422 if invalid
↓
4. get_db() runs — opens SessionLocal, yields db
↓
5. create_claim(payload, db) runs
↓
6. Claim(**payload.model_dump()) → db.add() → db.commit()
↓
7. db.refresh(claim) — reloads UUID + timestamps from DB
↓
8. FastAPI serialises return value through ClaimRead
↓
9. 201 response with JSON body
↓
10. get_db() finally block runs — db.close()

Steps 2–3 and 8 are handled automatically by FastAPI. Steps 4 and 10 are handled by Depends(get_db). You write steps 5–7.

Step 1
Pydantic schemas
bash
touch app/schemas.py
python — app/schemas.py
from datetime import datetime
from uuid import UUID

from pydantic import BaseModel


class ClaimCreate(BaseModel):
    """Fields the caller must provide when opening a new claim."""
    policy_id: UUID
    description: str
    status: str = "open"


class ClaimRead(BaseModel):
    """Shape of a claim returned from the API."""
    id: UUID
    policy_id: UUID
    description: str
    status: str
    created_at: datetime

    model_config = {"from_attributes": True}
💡 What does from_attributes = True do? By default Pydantic expects a dictionary. SQLAlchemy returns objects with attributes (not dicts). This flag tells Pydantic "read from object attributes" — without it, ClaimRead.model_validate(db_claim) would fail with a validation error.

Notice: ClaimCreate has no id or created_at — the DB generates those. ClaimRead has both — the API must return them.

Step 2
Session dependency

Open app/db.py. You already have engine and Base. Add SessionLocal and the dependency function at the bottom:

python — additions to app/db.py
from sqlalchemy.orm import sessionmaker, Session
from typing import Generator

SessionLocal = sessionmaker(autocommit=False, autoflush=False, bind=engine)


def get_db() -> Generator[Session, None, None]:
    """Yield a database session; close it when the request is done."""
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()
⚠ Check your existing imports in db.py before adding — avoid duplicating sessionmaker or Session if already present.

autocommit=False means changes are only persisted when you call db.commit() explicitly — no accidental writes. autoflush=False means SQLAlchemy won't emit SQL until you commit or query — keeps behaviour predictable.

Step 3
Claims router

Keep routes out of main.py — that file stays thin. Create a dedicated router module:

bash
mkdir -p app/routers
touch app/routers/__init__.py
touch app/routers/claims.py
python — app/routers/claims.py
from uuid import UUID

from fastapi import APIRouter, Depends, HTTPException
from sqlalchemy.orm import Session

from app.db import get_db
from app.models.claim import Claim
from app.schemas import ClaimCreate, ClaimRead

router = APIRouter(prefix="/claims", tags=["claims"])


@router.post("/", response_model=ClaimRead, status_code=201)
def create_claim(payload: ClaimCreate, db: Session = Depends(get_db)):
    claim = Claim(**payload.model_dump())
    db.add(claim)
    db.commit()
    db.refresh(claim)
    return claim


@router.get("/", response_model=list[ClaimRead])
def list_claims(db: Session = Depends(get_db)):
    return db.query(Claim).all()


@router.get("/{claim_id}", response_model=ClaimRead)
def get_claim(claim_id: UUID, db: Session = Depends(get_db)):
    claim = db.query(Claim).filter(Claim.id == claim_id).first()
    if not claim:
        raise HTTPException(status_code=404, detail="Claim not found")
    return claim

Line by line — the create route:

payload: ClaimCreate — FastAPI validates the request body automatically. Invalid body → 422, no code needed.

Claim(**payload.model_dump()) — converts Pydantic object to dict, unpacks as keyword args into the SQLAlchemy constructor.

db.add(claim) — stages the row. Not yet in Postgres.

db.commit() — writes to Postgres. UUID and timestamps are assigned here.

db.refresh(claim) — reloads the object from the DB so id and created_at are populated before returning.

response_model=ClaimRead — FastAPI passes the returned object through ClaimRead, filtering out any fields not in the schema.

Field note · real bug hit while building this slice
SQLModel vs. plain SQLAlchemy + Pydantic

FastAPI's official docs have a full SQL tutorial built on SQLModel — a library that merges a SQLAlchemy model and a Pydantic schema into one single class. Skimming that tutorial while working on a plain SQLAlchemy + Pydantic project (this project's actual stack) produces code that looks plausible but doesn't work.

python — SQLModel pattern (NOT this project's stack)
class Hero(SQLModel, table=True):
    id: int | None = Field(default=None, primary_key=True)
    name: str

@app.post("/heroes/")
def create_hero(hero: Hero, session: SessionDep) -> Hero:
    session.add(hero)          # works — Hero IS the DB model
    session.commit()
    session.refresh(hero)
    return hero

In SQLModel, session.add(hero) works directly because Hero is the database-mapped class — there's no separate Pydantic/SQLAlchemy split to bridge. Copying this pattern into a project using separate ClaimCreate (Pydantic) and Claim (SQLAlchemy) classes produces session.add(claim) where claim is a Pydantic object — which fails, because session.add() only accepts SQLAlchemy-mapped instances.

⚠ How to tell which tutorial you're reading: if the model class inherits from SQLModel and has table=True, that's SQLModel — a different library. This project's ADR-003 deliberately chose the split-class pattern (plain SQLAlchemy models + separate Pydantic schemas), so SQLModel examples don't transfer directly. Stick to plain FastAPI + SQLAlchemy docs, not the SQLModel tutorial section.
Field note
The bridge line — Pydantic in, SQLAlchemy out

This is the single most-repeated correction while building the create route. Neither Pydantic nor SQLAlchemy knows the other library exists. There is no automatic conversion between a validated ClaimCreate object and a database-ready Claim object — you write that conversion explicitly, by hand, every time.

python
claim_dict = claim.model_dump(exclude_unset=True)   # Pydantic → plain dict
claim_dict["status"] = "Submitted"                   # server-assigned fields
claim_dict["reference_number"] = str(uuid.uuid4())

db_claim = Claim(**claim_dict)   # ← THE BRIDGE — dict → real SQLAlchemy instance
session.add(db_claim)            # only Claim instances are valid here
session.commit()
session.refresh(db_claim)        # reload id, filed_at, updated_at
return db_claim                  # return the DB-backed object, not the input
💡 The pattern to memorise: session.add(), session.commit(), and session.refresh() must always operate on the same variable — the real Claim instance — never the original Pydantic input. Mixing the two (e.g. calling session.refresh(claim) when claim is still the Pydantic object) fails, because SQLAlchemy only tracks objects it created or that were explicitly added to the session.
Field note
Session vs. SessionLocal — factory vs. instance

A recurring type-annotation mistake: using SessionLocal as the type in Annotated[SessionLocal, Depends(get_db)], when the correct type is Session (from sqlalchemy.orm).

SessionLocal
A factory — created once via sessionmaker(bind=engine). Calling it, SessionLocal(), produces a new session instance. It is never itself the type of a value flowing through the app.
Session
The class of the object that get_db() actually yields. This is the correct type for the dependency annotation, because it describes what a route handler receives.
python — app/db.py
from sqlalchemy.orm import sessionmaker, Session   # ← both imported

SessionLocal = sessionmaker(bind=engine)             # factory

def get_db():
    db = SessionLocal()      # an instance — this is a Session
    try:
        yield db
    finally:
        db.close()

SessionDep = Annotated[Session, Depends(get_db)]     # ← Session, not SessionLocal

General rule: the type in Annotated[X, Depends(fn)] should always match what fn actually yields or returns — not the name of whatever helper was used to construct it.

Field note
session.execute() — the result isn't rows yet

Calling select(Claim) only builds a query — it doesn't run it. Calling session.execute(stmt) runs it, but returns a Result object, not usable rows directly. A common bug: chaining .scalars() on the wrong side, or forgetting it entirely.

python — WRONG
stmt = select(Claim).scalars().all()      # .scalars() on a statement — invalid, no rows exist yet
claims = session.execute(select(Claim))   # missing .scalars().all() — returns raw Result, not a list
python — CORRECT
# Single row (or None)
stmt = select(Claim).where(Claim.id == claim_id)
claim = session.execute(stmt).scalar_one_or_none()

# Many rows
stmt = select(Claim)
claims = session.execute(stmt).scalars().all()
MethodUse when
.scalar_one_or_none()Expecting exactly one row or none (e.g. lookup by id). Returns the object or None.
.scalars().all()Expecting a list of rows. Returns a plain Python list of model instances.
Field note
Model registration & the metadata gotcha

Real error hit during testing:

text — actual traceback
sqlalchemy.exc.NoReferencedTableError: Foreign key associated with
column 'claims.policy_id' could not find table 'policies' with which
to generate a foreign key to target column 'id'

This looks like a missing-data problem but isn't — it's an import problem. SQLAlchemy builds its internal map of tables by registering each model as its file is imported. If nothing in the app's import chain ever imports Policy or Customer — because the router only imports Claim — SQLAlchemy has no idea those tables exist, even though they're physically present in Postgres. The foreign key relationship is Python-level metadata, not something read live from the live DB schema.

✓ Fix: ensure every model gets imported somewhere in the app's startup path — typically via app/models/__init__.py importing all of them, so importing the package pulls in the full set.
python — app/models/__init__.py
from app.models.customer import Customer
from app.models.policy import Policy
from app.models.claim import Claim
Field note
Python-side defaults vs. database-side defaults

Real error hit while seeding test data directly via psql:

text — actual error
ERROR:  null value in column "created_at" of relation "customers"
violates not-null constraint

The model defines a default:

python — customer.py
created_at: Mapped[datetime] = mapped_column(
    DateTime, default=datetime.utcnow, nullable=False
)

This default= is a Python-side default — SQLAlchemy fills it in only when a row is inserted through SQLAlchemy (i.e. via session.add() / session.commit()). It is invisible to Postgres itself. Inserting a row with raw SQL via psql bypasses SQLAlchemy entirely, so nothing populates that column — and the NOT NULL constraint at the database level rejects the row.

💡 When seeding data by hand in psql, supply every column that has a Python-side (not database-side) default explicitly — e.g. created_at via now(). Only true database-level defaults (declared with server_default= in SQLAlchemy, or a DB-level DEFAULT in a migration) are filled in automatically by Postgres regardless of how the row is inserted.
Field note
Codespaces port visibility — browser 404 with a healthy server

Symptom: uvicorn starts cleanly, curl http://localhost:8000/health from inside the Codespace returns 200, but the same URL 404s in the browser.

This is not an app bug. If curl from inside the Codespace to the public forwarded URL also returns 200, the server and tunnel are both healthy — the failure is isolated to the browser tab itself, usually a stale/cached URL from an earlier Codespace session pointing at a dead tunnel.

1. curl localhost:8000/health → 200
↓ still failing in browser?
2. curl <public-url>/health from inside Codespace
↓ 200 here too → server/tunnel fine
3. Problem is browser-side: stale tab, cache, or wrong URL

Fix sequence: set the port to Public in the Ports tab (Private ports can behave inconsistently even for the owner) → open the URL fresh via the globe icon in the Ports tab, never a hand-typed or reused tab → hard refresh → try incognito if still failing, to rule out extensions/cache entirely.

⚠ A 404 from GitHub's tunnel proxy (wrong/stale URL) and a 404 from your own FastAPI app (no matching route) look identical in a browser. The curl -v test is what distinguishes them — check the response headers for x-served-by: tunnels-prod-... versus a plain FastAPI JSON 404 body.
