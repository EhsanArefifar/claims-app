Slice 3
Tests + Structured Logging
pytest coverage on the create/read claim path from Slice 2, plus structured logging on every request/response cycle.
Scope

Six pytest cases covering POST /claims (success + validation failure), GET /claims/{id} (found + not found), and GET /claims (list) — plus a structlog-based middleware logging every request's method, path, status code, and duration.

Parked, unchanged from ADR-003: status enum strategy, reference number strategy, Customer/Policy CRUD APIs.

Decisions this slice (→ ADR-004)
◆
Test isolation: a separate claims_test database in the same Postgres sidecar, chosen over transactional rollback — avoids a savepoint/commit conflict since the app's routes already call session.commit() themselves.
◆
Schema setup: Base.metadata.create_all() against the test engine, rather than running real Alembic migrations. Testing the migrations themselves is a separate, later concern.
◆
Per-test isolation: TRUNCATE ... CASCADE on every table before each test, rather than a wrapped transaction — simpler given the isolation choice above.
◆
Logging: structlog with JSONRenderer, kept as-is rather than swapping to ConsoleRenderer for dev — matches what a real log aggregator wants, and read fine raw during debugging.
▲
Open — stdlib log integration: uvicorn's and SQLAlchemy's own logs aren't routed through the structlog JSON pipeline yet; they print as plain text alongside it. Real integration needs structlog.stdlib.ProcessorFormatter. Deferred.
▲
Open — no custom exception handler: a genuine DB error (e.g. the FK violation below) still surfaces as a bare 500, and prints twice — once as the app's own structured unhandled_exception log, once as Starlette's default plain-text traceback. A proper @app.exception_handler is future work.
Environment
Test database & env vars
From a clean devcontainer, exactly what to run to get claims_test up and wired in.
1 · Create the test database

Same Postgres sidecar as the dev DB — connect to the default postgres maintenance database and create a second one alongside claimsdb.

2 · Set TEST_DATABASE_URL

Wherever DATABASE_URL is already defined for the devcontainer (the compose file's environment: block) — add TEST_DATABASE_URL right alongside it. A .env.example entry alone does nothing; the app only reads real environment variables.

environment block
environment: - DATABASE_URL=postgresql://claims:claims@db:5432/claimsdb - TEST_DATABASE_URL=postgresql://claims:claims@db:5432/claims_test
▲
Env var changes need a container rebuild, not just a save — "Rebuild Container" from the Codespaces/devcontainer command palette, or a fresh docker compose up if working outside Codespaces.
3 · Verify connectivity
bash
# from inside the devcontainer, after rebuild echo $TEST_DATABASE_URL # should connect with no error and return an empty table list — # claims_test has no tables yet until pytest creates them psql "$TEST_DATABASE_URL" -c '\dt'
A note on checking tables manually

Running \dt against claims_test right after a pytest run will still show no tables — that's expected, not a bug. The create_tables fixture is session-scoped: it builds the schema when the test session starts and calls drop_all() when it ends, so outside of an active test run the database is intentionally empty.

Part 1 · Testing
Fixture architecture
Four composed fixtures in conftest.py — each with one job, each requesting the one before it.
The chain
create_tables→ db_session→ seeded_db→ client

create_tables — session-scoped, requested by db_session. Runs once for the whole test session: Base.metadata.create_all(engine) against the claims_test engine, drop_all() on teardown.

db_session — function-scoped. Opens a plain session directly on the test engine, truncates every table (TRUNCATE ... RESTART IDENTITY CASCADE) before yielding, closes the session after. No connection/transaction wrapper — an earlier version tried wrapping the session in its own transaction for rollback-based cleanup, but that reintroduced the savepoint/commit conflict the separate-DB choice was meant to avoid (see Field Notes). Truncate-before-yield does the isolation work on its own.

seeded_db — function-scoped, depends on db_session. Inserts a real Customer and a Policy referencing it, commits, and returns both objects — so tests needing a valid policy_id pull it off a real row instead of hardcoding a UUID.

client — function-scoped, depends on db_session. Overrides get_db to yield the test session, wraps the app in TestClient, clears app.dependency_overrides on teardown.

client_no_db — a second, simpler client fixture with no DB dependency at all, for tests that never reach the database layer (health check, Pydantic validation failures).

Database

A second Postgres database, claims_test, created in the same sidecar as the dev DB. See the Environment page for the exact commands.

Part 2 · Logging
Structured logging
structlog wired in as middleware — every request logged, without touching route code.
Pipeline (logging_config.py)

Six processors, in order: merge_contextvars → add_log_level → TimeStamper (ISO, UTC) → StackInfoRenderer → format_exc_info → JSONRenderer. Logger factory is PrintLoggerFactory — structlog calls print() directly and never touches Python's stdlib logging module.

Middleware (middleware.py)

A BaseHTTPMiddleware subclass. Before calling the next handler: clears any leftover context, binds a fresh request_id (uuid4) plus method and path via structlog.contextvars.

Normal path — including FastAPI's own 4xx/5xx responses. ExceptionMiddleware sits inside this middleware in the stack, so a 404 or 422 is already a plain Response by the time call_next returns — it logs http_request with the real status code and duration. Confirmed against a live 404.

Crash path — a genuine unhandled exception. Logs unhandled_exception at error level with duration and full traceback via log.exception(...), then re-raises. Confirmed against a live FK violation.

import logging import structlog def configure_logging() -> None: """ Configure structlog for the application. Pipeline explanation: - merge_contextvars : merges any context bound via structlog.contextvars (used in the middleware to attach request_id, path, etc.) - add_log_level : adds the "level" key (info, warning, error…) - TimeStamper : adds "timestamp" in ISO-8601 format (UTC) - StackInfoRenderer : renders stack_info if present - format_exc_info : renders exception info into the "exception" key - JSONRenderer : serialises the whole event dict to a JSON string → one JSON object per line, easy to parse / ship to a log aggregator """ # Configure stdlib logging independently of structlog. # structlog uses PrintLoggerFactory (calls print() directly) and never # touches stdlib at all. basicConfig() only affects stdlib loggers such # as uvicorn's access log or SQLAlchemy's query log — setting the format # to "%(message)s" strips uvicorn's default prefix but leaves its lines # as plain text, NOT routed through the JSON pipeline above. # Net result: app logs → one-line JSON, uvicorn logs → plain text, # both in the same terminal. Real integration (ProcessorFormatter on # stdlib handlers) is a follow-up — see Open Questions in ADR-004. logging.basicConfig( format="%(message)s", level=logging.INFO, ) structlog.configure( processors=[ structlog.contextvars.merge_contextvars, structlog.stdlib.add_log_level, structlog.processors.TimeStamper(fmt="iso", utc=True), structlog.processors.StackInfoRenderer(), structlog.processors.format_exc_info, structlog.processors.JSONRenderer(), ], wrapper_class=structlog.make_filtering_bound_logger(logging.INFO), context_class=dict, logger_factory=structlog.PrintLoggerFactory(), )
Full source — middleware.py
import time import uuid import structlog from starlette.middleware.base import BaseHTTPMiddleware from starlette.requests import Request from starlette.responses import Response log = structlog.get_logger() class RequestLoggingMiddleware(BaseHTTPMiddleware): """ Logs every HTTP request with method, path, status code, and duration. Normal path (including FastAPI's own 4xx/5xx responses): FastAPI's ExceptionMiddleware sits *inside* this middleware, so a 404 from GET /claims/{id} or a 422 from bad input is already converted to a Response by the time call_next returns here. It reaches the log.info line with the correct status code and duration — the except block is never entered. Unhandled exception path (a genuine crash that bypasses FastAPI's handlers): The except block fires, computes duration_ms so timing is still captured, logs with log.exception (which includes the traceback), then re-raises so Starlette's ServerErrorMiddleware can return a 500. """ async def dispatch(self, request: Request, call_next) -> Response: # Fresh context for every request structlog.contextvars.clear_contextvars() structlog.contextvars.bind_contextvars( request_id=str(uuid.uuid4()), method=request.method, path=request.url.path, ) start = time.perf_counter() try: response: Response = await call_next(request) except Exception: # Log unhandled exceptions with duration before re-raising duration_ms = round((time.perf_counter() - start) * 1000, 2) log.exception("unhandled_exception", duration_ms=duration_ms) structlog.contextvars.clear_contextvars() raise # Normal path: log success with duration duration_ms = round((time.perf_counter() - start) * 1000, 2) log.info( "http_request", status_code=response.status_code, duration_ms=duration_ms, ) # Clean up so context doesn't bleed into background tasks structlog.contextvars.clear_contextvars() return response

Field notes
pytest discovery & fixtures
Three real bugs, one theme: names matter more than they look like they should.
1 Discovery pattern

A file named test.py was silently never collected. pytest's default discovery only matches test_*.py or *_test.py — an exact match on the word "test" doesn't qualify. Renamed to test_main.py, immediately collected.

2 Annotated alias as a dict key

app.dependency_overrides[SessionDep] = TestSessionDep, where both sides were Annotated[Session, Depends(...)] type aliases. This threw no error — dependency_overrides is a plain dict, and Python happily accepts any object as a key. But FastAPI looks up overrides by the actual callable passed to Depends(...) (get_db), not by an annotated type. The override silently matched nothing; the route would have hit the real dev DB. Fixed by using get_db itself as the key.

3 Fixture-as-parameter footgun

A generator function get_test_db was wrapped in @pytest.fixture, then requested by name as a parameter inside a second fixture. pytest resolved that parameter to whatever get_test_db yielded (a Session instance) — not the function object itself. The override then tried to assign a Session as the dependency override, which FastAPI can't call. Fixed by keeping get_test_db a plain, un-decorated generator function, referenced directly by name.

Field notes
Transactions & overrides
Two ways state can leak between tests when cleanup isn't explicit.
4 The savepoint/commit conflict

An early db_session fixture wrapped the test session in its own connection.begin() transaction, intending to roll it back after each test. But the app's routes call session.commit() themselves — and a session bound to an already-open connection-level transaction treats commit() as ending that transaction, not just flushing. The fixture's own transaction.rollback() then had nothing left to undo. This is exactly the gotcha that made transactional rollback the rejected option back when the test-DB strategy was chosen — it crept back in through the fixture implementation. Fixed by dropping the connection/transaction wrapper entirely: a plain session on the engine, TRUNCATE before yield, close after.

5 Uncleared dependency_overrides

An override set inline inside one test function body (app.dependency_overrides[get_db] = get_test_db), with no teardown, persists on the shared app object for every test that runs afterward — order-dependent and easy to miss, since a suite can pass by luck if tests happen to run in a forgiving order. Fixed by moving the override into a fixture with app.dependency_overrides.clear() after yield.

Field notes
UUIDs & payload traps
Small type and syntax mismatches that read correctly at a glance.
6 UUID vs str comparison

assert body["policy_id"] == policy.id — body comes from response.json(), so every value is a plain JSON type (str). policy.id is still a uuid.UUID object off the SQLAlchemy model. A str and a UUID are never equal to each other even for the same value — no implicit coercion. Fixed by comparing against the same string used to build the payload (str(policy.id)).

7 Dotted string, not attribute access

payload["policy.id"] — inside quotes, "policy.id" is a literal string containing a period, not dotted attribute access on a policy variable. The dict was built with the key "policy_id" (underscore), so this raised KeyError: 'policy.id'.

8 ForeignKeyViolation on an empty test DB

Sending a hardcoded policy_id that doesn't exist in the freshly truncated claims_test DB raises sqlalchemy.exc.IntegrityError / ForeignKeyViolation on insert. Expected, not a bug — resolved by the seeded_db fixture inserting a real Customer + Policy first and using its actual .id.

Field notes
Logging internals
What structlog actually touches, and what FastAPI's middleware stack actually does.
9 structlog never touches stdlib logging

With PrintLoggerFactory, structlog calls print() directly. logging.basicConfig(format="%(message)s") only affects Python's stdlib logging module — it strips uvicorn's default log prefix, but doesn't route uvicorn's or SQLAlchemy's logs through the JSON pipeline. Net effect: app logs are one-line JSON, uvicorn's are plain text, side by side in the same terminal. Real integration needs structlog.stdlib.ProcessorFormatter attached to the stdlib handlers — scoped as later work, not this slice.

10 Logging placement on the exception path

An early version computed duration_ms and logged http_request only after the whole try/except/finally block. A crashed request never reached that line — it got no log at all, exactly the request you'd most want timing data for. Fixed by computing duration and logging (unhandled_exception, with duration) inside the except branch as well.

11 Where FastAPI's own error responses actually get handled

FastAPI's ExceptionMiddleware sits inside custom BaseHTTPMiddleware in the stack. A 404 or 422 is already a normal Response by the time call_next returns to the middleware — it hits the ordinary success-path log line, never the except block. Only a genuinely unhandled crash (uncaught IntegrityError) reaches except. Confirmed against a live 404 and a live FK-violation crash side by side.

12 The duplicate traceback isn't a bug

An unhandled exception currently prints twice: once as the app's own structured unhandled_exception JSON line, and once as a second, plain-text traceback from Starlette's default ServerErrorMiddleware — which sits outside the custom middleware and does its own logging on the way to producing the 500 response. Not duplicated logic in the app; a real gap — no @app.exception_handler yet to intercept and return a clean JSON error body before Starlette's default takes over. Logged as an open question, not fixed this slice.
