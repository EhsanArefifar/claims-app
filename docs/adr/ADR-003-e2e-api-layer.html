ADR-003 · claims-app · Slice 2

API layer: schemas, session management, and routing

Decisions made while wiring FastAPI to Postgres for the first end-to-end Claims flow — request validation, database session lifecycle, route organisation, reference number generation, and model metadata registration.

Status
Accepted
Date
July 2026
Slice
2 — First End-to-End Flow
Stack
FastAPI · SQLAlchemy · Pydantic · Postgres
Context

Slice 1 established the data model — Customer, Policy, and Claim as SQLAlchemy models, migrated to Postgres. Nothing in the app could yet be called over HTTP. Slice 2's goal was the first real request/response cycle: create and read a claim through FastAPI endpoints backed by Postgres, no auth.

Five design decisions arose in the course of building this: how to separate the API's request/response contract from the database schema, how to manage the database session lifecycle per request, how to organise route handlers, how to generate a claim reference number given the model has no database-level default for it, and how to ensure SQLAlchemy correctly resolves foreign keys across model files.

Decisions
1
Separate Pydantic schemas from SQLAlchemy models
Dedicated app/schemas.py, ClaimCreate / ClaimRead split
Options
Separate schemas Reuse SQLAlchemy models directly SQLModel merged class
Rationale
SQLAlchemy models carry DB internals (session state, relationships) that Pydantic/FastAPI cannot serialise cleanly. The Create/Read split lets the API hide server-generated fields (id, filed_at, updated_at) from the request contract while exposing them in responses. This is the FastAPI-idiomatic pattern for a plain-SQLAlchemy stack and avoids coupling the API shape to the DB schema.
↕
Two parallel class hierarchies to maintain — a new field or a modification to an existing one must be applied in both the SQLAlchemy model and the relevant Pydantic schema(s). Accepted as the cost of keeping the API contract independent of the database schema.
2
Session-per-request via Depends(get_db)
Generator dependency, injected per route
Options
Dependency injection (yield) Global session Context manager per route
Rationale
The generator pattern (try / yield / finally) guarantees the session is closed after every request — including on exceptions — without duplicating teardown logic in every route. Dependency injection keeps routes testable: tests can override get_db to inject a test session pointed at a different database, without changing the routes or the request/response schemas at all.
↕
One session per request means one DB connection per request. Fine at this scale; SQLAlchemy's built-in connection pooling handles concurrency adequately.
3
Routes in a dedicated router module
app/routers/claims.py via APIRouter, registered in main.py
Options
Per-entity router modules All routes in main.py One flat routes.py
Rationale
Keeping main.py thin (app setup and router registration only) is a FastAPI best practice and a Twelve-Factor principle. Per-entity routers make it easy to add auth middleware, versioning, or tags per resource group later without touching unrelated routes.
↕
More files to navigate early on, for one entity. Pays off from Slice 4 onward when auth middleware is added per-router rather than globally.
4
Reference number generation — temporary placeholder
str(uuid.uuid4()) generated in the route handler
Options
App-side UUID string (temporary) Database sequence Human-readable claim number scheme
Rationale
Claim.reference_number is unique=True, nullable=False with no database-level default — Postgres cannot generate it on its own. Rather than alter the Slice 1 model mid-slice, the route handler generates a UUID string as a stand-in value before constructing the Claim instance. This unblocks the end-to-end flow without reopening the data model.
↕
Not a real business-facing claim number — just a placeholder that satisfies the not-null/unique constraint. A proper human-readable scheme (e.g. sequential per-year numbering) is deferred; see Open Questions.
5
Explicit model registration for foreign key resolution
app/models/__init__.py imports every model
Options
Central __init__.py import Rely on incidental imports
Rationale
Discovered during implementation that SQLAlchemy's foreign key resolution depends on all related models being imported somewhere in the app's startup path — this shaped the addition of app/models/__init__.py as an explicit registration point, rather than relying on incidental imports from whichever router happens to be loaded. Without it, Claim's foreign key to policies failed to resolve at commit time, because nothing in the request path imported Policy directly.
Consequences
Positive
  • Slice 3 testing becomes straightforward: tests send the same ClaimCreate/ClaimRead JSON shapes, but get_db is overridden to point at a separate test database — the schemas and routes stay untouched.
  • Slice 4 auth can add a get_current_user dependency without ever needing to change ClaimCreate — auth-related fields (e.g. a future created_by_user_id) stay off the API contract unless deliberately exposed.
  • Future API versioning (e.g. a ClaimReadV2) is possible without touching the Claim table or model at all.
  • The central model registration point (app/models/__init__.py) makes foreign key resolution explicit and predictable rather than dependent on which router happens to be imported first.
Negative / trade-offs
  • Any new field or modification to Claim must be applied in two places — the SQLAlchemy model and the relevant Pydantic schema(s) — with no automatic sync between them.
  • Implementation surfaced a real architecture-shaping surprise: a FastAPI/SQLModel tutorial pattern was initially followed by mistake, producing code (session.add() on a Pydantic object) that doesn't apply to this project's split-model stack. Cost real iteration time; documented as a field note to avoid repeating.
  • The reference number placeholder is not production-appropriate and will need revisiting before this feature is client-facing.
Open questions
?
What is the real reference number generation strategy? Currently a random UUID string, not a business-readable claim number. Needs a proper scheme (e.g. sequential, per-year, or prefixed by claim type) — deferred to a future slice once real requirements are clearer.
?
Should status be a constrained enum rather than a free String? Claim.status is currently an unconstrained String column. A proper enum (Postgres native type or Pydantic Literal) would prevent invalid status values, but requires a migration — out of scope for this slice.
?
Should Customer and Policy get their own CRUD APIs? Both are currently seeded directly via psql for testing. Whether they need full API-driven management, or remain reference data managed some other way, is undecided.
