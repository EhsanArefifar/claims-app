ADR-004 · claims-app · Slice 3

Test Isolation Strategy & Structured Logging

How the create/read claim path gets tested in isolation from the dev database, and how every request gets logged.

Status
Accepted
Date
July 2026
Slice
3 — Tests + Structured Logging
Stack
pytest · structlog · SQLAlchemy · PostgreSQL
Context

Slice 2 delivered POST /claims and GET /claims against the dev database with no automated tests and no logging beyond uvicorn's default access log. This slice adds pytest coverage over that path and structured logging over every request, without changing any route code.

Testing against a real database meant deciding how to keep test runs from touching or depending on dev data, and how to reset state between individual tests. Logging meant picking a library and a request-cycle strategy that captures both successful and failed requests.

Decisions
1
Test database isolation strategy
Separate test database
Options
Separate DB Transactional rollback
Rationale
Managing a second database (claims_test) is simpler than layering rollback logic on top of the main database. The app's routes already call session.commit() themselves, which complicates a rollback-based approach — a separate database sidesteps that entirely.
2
Schema setup for the test database
Base.metadata.create_all()
Options
create_all() Real Alembic migrations
Rationale
Migrations themselves aren't under test yet — this slice only tests the API layer. Building the schema straight from the models is sufficient for that.
↕
Whether alembic upgrade head actually reproduces this schema isn't exercised by any test. Deferred until migrations themselves need testing.
3
Per-test isolation mechanism
TRUNCATE ... CASCADE before each test
Options
Truncate before each test Transaction rollback per test
Rationale
Truncating clears every table before each test runs, so there's no dependency on how the previous test ended. If a test fails partway through, the next one still starts from a guaranteed-clean set of tables — no special recovery logic needed for a mid-test failure.
4
Logging library and output format
structlog + JSONRenderer
Options
structlog · JSONRenderer structlog · ConsoleRenderer
Rationale
Setting up a nicer console renderer isn't the core logging problem this slice needed to solve, and JSONRenderer's output proved readable enough directly in the terminal while debugging. Not worth the extra setup right now.
↕
Less visually scannable during local development than a colorized console renderer would be. Can revisit if it becomes a real friction point.
Consequences
Positive
  • Tests run against a real Postgres database, so no dialect-specific surprises versus dev/prod
  • A failed test doesn't leave the database in a state that affects the next test — no dependency on execution order
  • Every request now produces a structured, timestamped log line with timing data, including on the crash path
  • Logging was added entirely as middleware — zero changes to route code
Negative / trade-offs
  • Test-DB schema isn't guaranteed to match what a real migration run would produce, since create_all() bypasses Alembic entirely
  • Third-party logs (uvicorn, SQLAlchemy) remain plain text, splitting terminal output between two formats
  • Unhandled DB errors still return a bare 500 to callers, with a duplicated traceback printed alongside the structured log
Open questions
?
When do uvicorn's and SQLAlchemy's logs get routed through the same JSON pipeline? Needs structlog.stdlib.ProcessorFormatter wired onto the stdlib handlers. Postponed until the AI agent subsystem (Phase D) is in place — a good candidate task to hand to the agent rather than do by hand now.
?
When does a custom exception handler replace the bare 500 / duplicated traceback? A proper @app.exception_handler for cases like IntegrityError would return a clean JSON error body instead. Same deferral as above — postponed to Phase D.
